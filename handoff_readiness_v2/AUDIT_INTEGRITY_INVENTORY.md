# GSP-CRV2-04 Phase 1 — audit-record and sensitive-read inventory

Built before any implementation, from `urls.py`, the Django model registry and
`pg_catalog`. Nothing here was found by searching for calls to the new helpers.

## 1. Audit records in scope

| Record | Table | Written by | Protection before this handoff |
|---|---|---|---|
| Decision audit | `competition_decision_audit_event` | `CompetitionDecisionWriteMixin`, engine close/default paths | `Model.save()` raised on re-save. Nothing below it. |
| Operator audit | `competition_operator_audit_event` | `core.services.lifecycle.operator_action` | Same. |
| Resolution manifest | `competition_resolution_manifest` | `prepare_manifest` / `complete_manifest` | **None.** No immutability guard at any layer. |
| Recovery audit | `<backup_root>/recovery-audit.jsonl` | `competition_backup.append_recovery_audit` | Append mode + `fsync`. No integrity check. |

The manifest is the one record written twice by design — once before the round
is resolved, once when it completes — so a blanket "no `UPDATE`" rule would have
broken round resolution. It is frozen from the moment `completed_at` is set,
which is the moment it becomes evidence.

## 2. Database roles and ownership

Observed on `192.168.50.38/globalstrat_plus`:

```
current_user = donwh
competition_decision_audit_event   owner donwh
competition_operator_audit_event   owner donwh
competition_resolution_manifest    owner donwh
has_table_privilege(donwh, …, UPDATE) = t
has_table_privilege(donwh, …, DELETE) = t
triggers on any competition_* table  = none
```

**The application connects as the owner of the tables it audits.** That single
fact decides the design. Revoking `UPDATE`/`DELETE` from the connecting role
does nothing while that role owns the table and can grant it straight back, and
an owner can drop any trigger it is subject to. So the work splits in two:

* what can be **rejected** — every write the application can make, at any
  layer, stopped by triggers that do not care which layer it came from;
* what can only be **detected** — a change made by whoever holds the
  maintenance credentials, caught by a hash chain whose head is written outside
  the database.

A third layer, `install_audit_guards --role-sql`, provisions a non-owner login
role for the application, which converts part of the second category into the
first. It is a deployment action, recorded in the operations guide, not
something this handoff could switch on for a running stack.

## 3. Registered read routes that can disclose decisions or audit payloads

Generated by `manage.py dump_read_inventory` into
`backend/core/services/read_inventory.json`, from the URL conf crossed with the
model registry. 31 sensitive read routes: 2 audit, 29 decisions; 30 logged,
1 exempt.

Two inventory bugs were found and fixed while building it, both of the kind
that produces a confident and wrong coverage number:

* **Substring matching.** `Decision` matched `DecisionLockedMixin` and
  `DecisionStatusView`, putting `programs.ProgramViewSet` and
  `course.DecisionStatusView` on the list as decision readers when neither
  serves a decision row. Whole-identifier matching removed both.
* **Reading only the class.** `RoundControlView` touches `OperatorAuditEvent`
  inside a module-level helper, so a class-scoped scan reported it as touching
  no audit record. The scan now also reads module-level functions the class
  calls by name — which is how that route came to be on the list at all, and
  then to be exempted deliberately.

### Exemptions

| View | Reason |
|---|---|
| `round_control.RoundControlView` | Reads `OperatorAuditEvent` only to count operator actions for the round-status block. No audit row, payload or decision is serialized. |

### Coverage mechanism

`core.middleware.SensitiveReadLogMiddleware` matches on
`request.resolver_match.route` against the inventory. A view registered later
that serves decision rows appears in the live inventory immediately and fails
`dump_read_inventory --check` until it is either logged or exempted on the
record. `test_the_inventory_route_format_is_what_a_request_resolves_to` exists
because an inventory and a middleware that spell routes differently would leave
every assertion about the inventory passing and nothing at all being logged.

## 4. Mapping every inventory row to a disposition

| Inventory row | Disposition |
|---|---|
| 4 audit records (3 tables + 1 file) | Covered: append-only triggers, hash chain, external anchor |
| `competition_resolution_manifest` two-phase write | Covered by a rule specific to it: mutable until `completed_at`, frozen after |
| `competition_audit_chain` (new) | Covered: same append-only trigger as the records it protects |
| `competition_sensitive_read_event` (new) | Covered: same trigger, and chained |
| 30 logged read routes | Covered by middleware, proven by resolver-format and end-to-end tests |
| 1 exempt read route | Exempt with the reason above |
| Application role = table owner | **Not closed by code.** Deployment action; SQL provided and tested, switch recorded as an open item |
